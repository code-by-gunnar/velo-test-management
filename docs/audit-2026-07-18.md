# Velo Test Management — Audit Report

**Date:** 2026-07-18
**Scope:** `apps/api` (Fastify 5), `apps/web` (Next.js 16 Pages Router), `packages/types`, DB migrations
**Method:** Three parallel reviews — security, performance, correctness — reading source directly and cross-checking against the documented architecture.

## Overall Assessment

The codebase is well-built. Verified strengths: RLS-backed multi-tenancy with a compile-time-branded `WorkspaceSql` type, uniformly parameterized SQL (postgres.js tagged templates, no string concatenation), hashed API keys / OTPs / reset+invite tokens, fail-closed sessions with a deactivation blocklist, correct AES-256-GCM (random IV, auth tag verified), and external I/O (Linear, R2, Anthropic, webhooks, email) consistently kept outside DB transactions so pool connections aren't pinned.

The findings below are real but mostly bounded. Priority order is at the bottom.

### 19. NEW (self-host): app connects to Postgres as superuser — RLS layer inert — FIXED 2026-07-18
Discovered while testing the #1 fix: tables use `FORCE ROW LEVEL SECURITY`, but the compose stack connects as `velo`, which the postgres image creates as a **superuser** — and superusers bypass RLS entirely, FORCE or not. **Correction to the original audit:** Railway's provisioned `postgres` user is also a superuser, so RLS was inert in production too — "RLS-backed multi-tenancy" was never actually exercised; the explicit `workspace_id = current_setting(...)` predicates were always the real isolation layer.

**Fixed:** `server.ts` provisions a non-superuser `velo_app` on boot when `APP_DB_PASSWORD` is set (create/alter role, grants, default privileges); compose points runtime `DATABASE_URL` at `velo_app` and migrations/fixups at `MIGRATION_DATABASE_URL` (superuser). Verified live: `velo_app` sees 0 tenant rows without `app.workspace_id`, correct rows with it; full login→cases e2e passes.

**Scoped exemption (follow-up):** `workspace_members` gets an `app_members_access USING (true)` policy for `velo_app` only — ~20 bare-`sql` call sites (login JWT claims, role checks, member management) query it without workspace context and always have (RLS never bound them in any environment). Content tables (test_cases, runs, etc.) are fully RLS-enforced. Closing the exemption needs an `app.user_id` policy + `withUser()` helper + call-site refactor.

## Critical / High — fix first

### 1. Cross-tenant data leak on SSE run stream — CONFIRMED
**File:** `apps/api/src/routes/runs.ts:480-548` (publisher: `run-items.ts:143-160`)

The stream endpoint validates `request.workspaceId === workspaceId` and `isUuid(runId)` but never confirms the run belongs to that workspace. The initial stats DB read is RLS-scoped (returns empty for a foreign run), but the Valkey pub/sub channel `run:${runId}` (line 529) is global and unscoped. A member of workspace A who obtains a run ID from workspace B can subscribe and receive that run's live pass/fail stats and case titles as testers execute it.

**Exploit:** `GET /api/workspaces/A/runs/<B-runId>/stream?token=...` — the A===A check passes, then live `run_update` events for B stream in.

**Fix:** Inside `withWorkspace`, `SELECT 1 FROM test_runs WHERE id = ${runId}` and return 404 if absent before subscribing. Optionally namespace the channel as `run:${workspaceId}:${runId}`.

### 2. Viewers can rename and delete projects (broken access control)
**File:** `apps/api/src/routes/workspaces.ts:499` (PATCH), `:561` (DELETE)

Both handlers only check workspace membership — no role guard, unlike every other mutating route (`test-cases.ts`, `run-items.ts` use `requireEditor`/`requireAdmin`). A read-only viewer can soft-delete an entire project or break deep links by changing `project_key`. Project *creation* (`workspaces.ts:220`) correctly rejects viewers, so this is an inconsistency.

**Fix:** Add `{ preHandler: [requireEditor] }` to PATCH and `requireAdmin` to DELETE. One line each.

### 3. OAuth account takeover via unverified provider email
**File:** `apps/web/src/auth.ts:90`, `apps/api/src/routes/auth.ts:436-453`

`oauth-signin` auto-links a new OAuth identity to an existing local account by matching email, without checking the provider asserted the email as verified. GitHub surfaces unverified primary emails and the web `signIn` callback forwards `profile.email` with no verification gate.

**Exploit:** Victim has verified password account `victim@corp.com`. Attacker creates a GitHub account, adds `victim@corp.com` as an unverified email, signs in with GitHub → backend auto-links to the victim's account → attacker gains full workspace access.

**Fix:** Only auto-link when the provider asserts the email is verified — `profile.email_verified === true` (Google); call `/user/emails` and require `verified: true` for the primary (GitHub). Otherwise require an explicit link flow while logged in.

### 4. Outbound webhook SSRF at delivery time
**File:** `apps/api/src/routes/webhooks.ts:323` (test-ping), `apps/api/src/queues/webhook.worker.ts:24` (delivery)

`isPrivateUrl()` runs only at webhook creation/update. Delivery and test-ping call `fetch` with default `redirect: "follow"` and no re-validation. Two bypasses: (1) the registered public endpoint 302-redirects to `169.254.169.254` (cloud metadata) or an internal service; (2) DNS rebinding — register a hostname resolving to a public IP, re-point it to a private IP before delivery. `isPrivateUrl` also only matches literal IP hostnames, so a hostname that *resolves* to a private IP passes creation validation.

**Fix:** At fetch time use `redirect: "manual"` and reject 3xx (or cap + re-validate each hop); resolve the hostname and block private / link-local / metadata ranges (incl. IPv6 `::1`, `fc00::/7`, `fe80::/10`, IPv4-mapped, decimal/octal encodings) before connecting — ideally pin the validated IP or route through an egress allowlist.

### 5. Three high-frequency N+1 insert loops (top performance issue)
- `apps/api/src/routes/runs.ts:120-133` — run creation inserts `run_items` one-per-case in a loop; fires on **every "Start Run"** (up to 500 sequential inserts in a single transaction, pinning 1 of 20 pool connections). Also `:403-416` (rerun-failures).
- `apps/api/src/routes/ingestion.ts:166-192, 370-395` — CI ingestion inserts one row per test result; fires on **every CI pipeline run** (1000+ inserts common). Highest-frequency N+1 in production.
- `apps/api/src/routes/test-cases.ts:747-849` — CSV import inserts cases + steps row-by-row (~2000 round-trips for a 500-row file). Position/tier-count queries are already cached; the data inserts are not batched.

**Fix:** Replace each loop with a single bulk `INSERT ... SELECT` / `unnest(...)`.

### 6. Vercel gateway ~4.5MB body limit breaks advertised 10MB uploads
**File:** `apps/web/src/pages/api/backend/[...path].ts:18-76`

The proxy fully buffers request and response bodies in memory. The API advertises `MAX_FILE_SIZE = 10MB` for evidence (`run-item-attachments.ts:18`), but Vercel Node functions hard-cap request/response bodies at ~4.5MB. Uploads between 4.5–10MB fail at the platform layer before reaching validation. Large export ZIPs (`export.ts`) fail the same way even though `archiver` streams correctly on the Railway side.

**Fix:** Route large binary transfers (evidence upload, export download) directly to the Railway API via a short-lived signed URL/token, bypassing the Vercel gateway.

## Low / Informational

- Session trusts the JWT role if the membership row is hard-deleted without a Valkey blocklist entry (`session.plugin.ts:127-138`) — recommend fail-closed: clear session context when the membership lookup returns no active row.
- CI-ingested `run_items` have `executed_at = NULL`, so CI failures are excluded from the "fragile cases" report but included in run-trend — inconsistent (`reports.ts:58-75` vs `ingestion.ts:179-191`). Use `COALESCE(ri.executed_at, tr.completed_at)` or set `executed_at = NOW()` on insert.
- No ingestion idempotency — a retried CI upload creates a duplicate run, skewing trend charts (`ingestion.ts:150-213, 354-416`). Accept an optional idempotency key.
- Hard-deleting a run orphans its R2 evidence objects (`runs.ts:567-578`) — DB cascades clean, R2 objects leak. Enumerate `r2_key`s and best-effort delete.
- JUnit XML parser doesn't explicitly disable entity expansion — billion-laughs memory-DoS possible on a large payload; `/ingest/*` endpoints are unthrottled (`ingestion.ts:37`, `lib/junit-parser.ts:22`).
- No "last admin" protection — an admin can demote/deactivate all other admins (self-deactivation is blocked) (`members.ts`).
- GCM IV is 16 bytes vs the NIST-recommended 12 (`lib/encryption.ts:8`) — functionally fine with random IVs, no reuse risk observed.
- v1 rate limiter is a fixed-window counter that fails open on Valkey error (`lib/rate-limiter.ts:33,62`) — allows ~2× burst at window boundaries.
- `report_viewed` PostHog event fires only on cache miss, so undercounts within the 60s cache window (`reports.ts:31-119`).
- `build` script (`package.json:6`) still uses the Windows-broken `--filter='./apps/*'` path form. The `dev` script (line 5) is already fixed to name-based filters.

## Investigation: slow suite-click / test-case retrieval

**Symptom:** Clicking into a test suite is slow to retrieve and display cases, even when the suite has only a handful of cases.

**Root cause — Vercel gateway cold start (measured, not assumed).**

Timing evidence (2026-07-18, production):

```
Through Vercel gateway:  attempt 1 = 1.52s   attempt 2 = 0.12s
Direct to Railway:       attempt 1 = 0.12s   attempt 2 = 0.16s
Railway /health:         ~0.16–0.29s (warm throughout)
```

Every client-side data fetch is funneled through the Next.js gateway function `apps/web/src/pages/api/backend/[...path].ts`. That function is a serverless invocation; when cold it takes **~1.4s to initialize** before it even forwards to Railway (1.52s first hit → 0.12s once warm). Railway and the `GET /cases` query itself are fast throughout (~120ms). Case count is irrelevant — the cost is fixed function-init overhead, which is why it's slow even with few cases.

Worse on the first interaction after idle, and worse on initial page load because `useSuiteTree` and `useTestCases` fire two concurrent gateway calls (`CasesPage`), so two cold instances can spin up at once. Once warm, navigation between suites is fast.

**Secondary overhead traced (real but not the symptom — tens of ms, not seconds):**
- Double network hop: browser → Vercel gateway → Railway.
- Per-request Valkey session lookup (`session.plugin.ts:109`).
- `withWorkspace` opens a 4-round-trip transaction (`BEGIN` / `SET LOCAL app.workspace_id` / `SELECT` / `COMMIT`) per read (`tenant.ts`), even for read-only GETs.

**Fixes, in order of impact:**
1. **Enable Fluid Compute on the Vercel project** — the actual fix. Fluid Compute reuses warm function instances instead of one-request-per-instance, largely eliminating these cold starts. It's the current Vercel default; if this project has it off, that explains the 1.5s. Vercel dashboard/config change.
2. **Warm the gateway on app load** — fire a cheap `GET /api/backend/health` when the app shell mounts so the function is warm before the user clicks a suite. Code-side mitigation.
3. **Collapse the `withWorkspace` transaction for single reads** — a read-only `GET /cases` doesn't need `BEGIN…COMMIT`; set `app.workspace_id` via `SELECT set_config(..., true)` in one round trip. Cuts 3 round trips to 1, shaving ~50–100ms off the warm path. Secondary.
