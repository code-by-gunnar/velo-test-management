# Plan 13-01: GWT Step Editor

## Goal
GWT projects get a dedicated keyword-aware step editor. When `test_format` is `'gwt'`, CasePanel renders GwtStepEditor instead of StepEditor. Each step has a keyword pill (Given/When/Then/And/But) and a single text field. Keywords auto-suggest based on position.

## Requirements Covered
- **GWT-10**: CasePanel renders GWT editor when project's test_format is 'gwt'
- **GWT-11**: Each GWT step has a keyword pill on the left and single text field — no expected_result column
- **GWT-12**: Keywords auto-suggest: first→Given, Given→When, When→Then, Then→Then. User can override
- **GWT-13**: Keyword pill is a clickable dropdown showing all five keywords
- **GWT-14**: Preconditions field remains available in GWT mode
- **GWT-15**: Keyboard navigation matches traditional editor

## Success Criteria (from ROADMAP)
1. When `test_format` is `'gwt'`, CasePanel renders GwtStepEditor instead of StepEditor
2. Each step shows a keyword pill on the left (clickable dropdown) and a single text input on the right
3. First step auto-defaults to Given; subsequent steps auto-suggest the next logical keyword
4. User can override the keyword by clicking the pill and selecting from the dropdown
5. Preconditions textarea remains above the step editor
6. Keyboard: Tab moves pill→text, Enter/Tab at text end adds new step, Backspace on empty deletes

### Task 3: Create GwtStepRow component

**New file:** `apps/web/src/components/cases/GwtStepRow.tsx`

Parallel to StepRow but with keyword pill + single text field instead of two-column.

```tsx
interface GwtStepRowProps {
  index: number
  action: string
  keyword: GwtKeyword
  isLast: boolean
  readOnly?: boolean
  onChangeText: (index: number, value: string) => void
  onChangeKeyword: (index: number, keyword: GwtKeyword) => void
  onAddAfter: (index: number) => void
  onDelete: (index: number) => void
  pillRef: React.RefCallback<HTMLButtonElement>
  textRef: React.RefCallback<HTMLTextAreaElement>
  onFocusPill: () => void
  onFocusText: () => void
}
```

**Layout:** Single row with `flex items-start gap-2`:
- Left: `<KeywordPill>` (fixed width ~60px)
- Right: `<textarea>` (flex-1, same auto-resize behavior as StepRow)

**Keyboard navigation:**
- **Tab on pill** (no Shift): move focus to text field → `onFocusText()`
- **Tab on text** (no Shift): add new step after current → `onAddAfter(index)`
- **Enter on text** (no Shift): add new step after current → `onAddAfter(index)`
- **Shift+Tab on text**: move focus back to pill → `onFocusPill()`
- **Backspace on empty text** (when index > 0): delete step → `onDelete(index)`
- **Backspace on pill** (when text is empty AND index > 0): delete step → `onDelete(index)` — mirrors traditional editor's "Backspace on first field when empty" pattern

**Auto-resize:** Same pattern as StepRow — `autoResize` on input, callback ref for mount resize.

### Task 4: Create GwtStepEditor component

**New file:** `apps/web/src/components/cases/GwtStepEditor.tsx`

Parallel to StepEditor but using GwtStepRow. Manages keyword auto-suggest.

```tsx
import { type Step } from "./StepEditor"
import { type GwtKeyword } from "./KeywordPill"

interface GwtStepEditorProps {
  steps: Step[]
  onChange: (steps: Step[]) => void
}
```

**Auto-suggest logic** — `suggestKeyword(steps, index)`:

```typescript
function suggestKeyword(steps: Step[], index: number): GwtKeyword {
  if (index === 0) return "given"
  const prev = steps[index - 1]?.step_type
  switch (prev) {
    case "given": return "when"
    case "when": return "then"
    case "then": return "then"
    case "and":
    case "but":
      // Inherit from the last non-and/but keyword
      for (let i = index - 1; i >= 0; i--) {
        const kw = steps[i].step_type
        if (kw && kw !== "and" && kw !== "but") {
          return kw === "given" ? "when" : kw === "when" ? "then" : "then"
        }
      }
      return "then"
    default:
      return "given"
  }
}
```

**handleAddAfter** — creates new step with auto-suggested keyword:

```typescript
const handleAddAfter = (index: number) => {
  const suggestedKeyword = suggestKeyword(steps, index + 1)
  const next = [
    ...steps.slice(0, index + 1),
    { action: "", expected_result: "", step_type: suggestedKeyword },
    ...steps.slice(index + 1),
  ]
  onChange(next)
  setTimeout(() => focusElement(index + 1, "text"), 0)
}
```

**Ensure at least one step** — same useEffect as StepEditor but with `step_type: "given"`:

```typescript
useEffect(() => {
  if (steps.length === 0) {
    onChange([{ action: "", expected_result: "", step_type: "given" }])
  }
}, [steps.length, onChange])
```

**handleChangeKeyword:**

```typescript
const handleChangeKeyword = (index: number, keyword: GwtKeyword) => {
  const next = steps.map((s, i) => (i === index ? { ...s, step_type: keyword } : s))
  onChange(next)
}
```

**handleChangeText:**

```typescript
const handleChangeText = (index: number, value: string) => {
  const next = steps.map((s, i) => (i === index ? { ...s, action: value } : s))
  onChange(next)
}
```

**Ref management:** Same `elementsRef` pattern as StepEditor but with keys `"${index}-pill"` and `"${index}-text"` instead of `"${index}-action"` and `"${index}-expected"`.

**Rendering:** No column headers needed (keyword pills are self-documenting). Map steps to GwtStepRow components.

## API Save Path (already wired)
- `CasePanel.onSubmit` (line 121-149) sends the `steps` array directly in the body. Since Step objects now include `step_type`, the API receives it automatically — no additional serialization needed.
- `GET /cases/:id` already returns `step_type` on each step (Phase 1 work), so view mode and edit-mode hydration both work.
- The API defaults `step_type` to `'action'` when omitted, so traditional projects are unaffected.

## Backwards Compatibility
- Step interface adds optional `step_type` — all existing code works unchanged
- Traditional StepEditor is untouched — only conditionally bypassed when `testFormat === "gwt"`
- API already handles `step_type` defaults — omitting it defaults to `"action"`
- View mode shows traditional layout for existing projects

## Edge Cases
1. **Switching from view to edit in GWT mode:** Steps loaded from API include `step_type` — GwtStepEditor uses them directly
2. **Empty step_type in API response:** Fallback to `"given"` for GWT display, `"action"` for traditional
3. **Keyword dropdown click-outside:** Closes dropdown without changing keyword
4. **Single step delete:** Blocked (same as traditional — `steps.length <= 1` guard)
5. **Copy/paste multiline text:** Stays in single text field (no auto-split). Expected — users can manually split later
6. **Steps saved with step_type in traditional project:** No harm — step_type defaults to `"action"`, traditional editor ignores it
