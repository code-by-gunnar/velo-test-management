# Plan 14-01: GWT Execution Adaptation

## Goal
GWT test cases execute as whole scenarios with a single pass/fail verdict. The execution screen detects the project's `test_format` and renders GWT steps read-only with keyword labels instead of the traditional Action/Expected table. No per-step status controls for GWT. Dashboard and results unchanged (already case-level).

## Requirements Covered
- **GWT-16**: In GWT projects, test run execution shows the full scenario but pass/fail is set at the case level, not per-step
- **GWT-17**: Execution screen for GWT cases shows steps as read-only with keyword labels, plus a single status dropdown for the whole scenario
- **GWT-18**: Run dashboard and results display work identically for GWT and traditional cases (case-level counts)

## Success Criteria (from ROADMAP)
1. Test run execution screen detects the project's `test_format` and adapts the UI
2. For GWT cases: steps render read-only with keyword labels, no per-step status controls
3. A single status dropdown (Pass/Fail/Blocked/Skipped) applies to the entire scenario
4. Run dashboard, results summary, and export all work identically — they operate at case level regardless of format

### Task 2: Render GWT steps in ExecutionScreen

**Modify:** `apps/web/src/components/runs/ExecutionScreen.tsx`

**2a. Add testFormat to component props:**

Find the props interface and add `testFormat: string`. Accept in destructuring.

**2b. Conditionally render GWT step layout (lines 475-514 — the steps table):**

Replace the entire step table block with a conditional:

```tsx
{!loadingCase && !isCaseDeleted && steps.length > 0 && (
  testFormat === "gwt" ? (
    <div className="rounded-lg border border-gray-200 bg-white mb-4 overflow-hidden">
      <div className="divide-y divide-gray-50">
        {steps.map((step) => (
          <div key={step.step_order} className="flex items-start gap-3 px-4 py-3">
            <span className="shrink-0 w-[60px] rounded bg-gray-100 px-2 py-1 text-xs font-medium text-gray-700 text-center mt-0.5">
              {(step.step_type ?? "given").charAt(0).toUpperCase() + (step.step_type ?? "given").slice(1)}
            </span>
            <p className="flex-1 text-sm text-gray-800 whitespace-pre-wrap">
              {step.action}
            </p>
          </div>
        ))}
      </div>
    </div>
  ) : (
    /* existing traditional table — unchanged */
  )
)}
```

**Key design points:**
- No column headers for GWT (keyword pills are self-documenting)
- No step number column (BDD scenarios are sequential by nature)
- No "Expected Result" column (GWT steps have action text only)
- Step comment icons STILL appear for GWT steps (annotations are useful regardless of format)
- The case-level verdict controls (P/F/B/S keyboard, status buttons) are UNCHANGED — they already apply to the whole case

**2c. Update CaseStep interface (if step_type not already present):**

Check lines 24-28 of ExecutionScreen.tsx. The `CaseStep` interface may not include `step_type`. Add it:

```typescript
interface CaseStep {
  step_order: number
  action: string
  expected_result: string
  step_type?: string
}
```

## GWT-18: Dashboard — No Changes Needed

The run dashboard (`apps/web/src/pages/app/[slug]/[projectKey]/runs/[runId]/index.tsx`) already operates at case level:
- Stats computed from `run_items.status` counts (pass/fail/blocked/skipped/untested)
- Results table shows case-level rows with verdict badges
- No per-step aggregation exists anywhere
- SSE updates push case-level stats

**GWT-18 is satisfied by default.** No modifications needed.

## Backwards Compatibility
- `testFormat` defaults to `"steps"` — existing runs render traditional table
- Case-level verdict controls unchanged — keyboard shortcuts (P/F/B/S) work identically
- Step comments still available for GWT steps
- Dashboard/stats/SSE completely unaffected

## Edge Cases
1. **Mixed-format runs:** Not possible — runs belong to a project, and projects have one format
2. **CI-ingested items:** step_type defaults to 'action' from API; CI items in GWT projects render correctly if step_type is set during ingestion
3. **No steps:** "No steps defined" message unchanged — applies to both formats
