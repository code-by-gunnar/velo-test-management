# Plan 15-01: GWT CSV Import — Keyword Column Support

## Goal
GWT projects can import BDD scenarios from CSV files with a keyword column mapped to `step_type`. Keyword values are normalized (case-insensitive, trimmed). Traditional projects are unaffected.

## Requirements Covered
- **GWT-19**: CSV import adds a `colKeyword` query parameter for mapping the keyword column
- **GWT-20**: When `colKeyword` is mapped, each imported row creates a step with the corresponding `step_type`
- **GWT-21**: Keyword column values are case-insensitive and trimmed
- **GWT-22**: If `colKeyword` is not mapped in a GWT project, imported steps default to `step_type: 'given'`

## Success Criteria (from ROADMAP)
1. CSV import adds a `colKeyword` query parameter for mapping the keyword column
2. Mapped keyword values are normalized: case-insensitive, trimmed, validated against allowed values
3. Each imported row creates a step with the corresponding `step_type`
4. If `colKeyword` is not mapped for a GWT project, imported steps default to `step_type: 'given'`
5. Import still works identically for traditional-format projects (step_type defaults to 'action')

**1d. Update row parsing to extract keyword:**

In the row processing loop where steps are built, extract the keyword value from the mapped column and normalize it:

```typescript
const VALID_KEYWORDS = new Set(["given", "when", "then", "and", "but"])

// Inside the step building logic:
let stepType: string | undefined
if (cols.keyword !== undefined) {
  const raw = (row[cols.keyword] ?? "").toString().trim().toLowerCase()
  if (VALID_KEYWORDS.has(raw)) {
    stepType = raw
  }
  // Invalid/empty values: leave undefined (caller decides default)
}

steps.push({
  action: row[cols.action!] ?? "",
  expected_result: row[cols.expected!] ?? "",
  step_type: stepType,
})
```

## Backwards Compatibility
- `colKeyword` is optional — omitting it keeps traditional behavior
- `step_type` in INSERT defaults to `'action'` when not set — existing imports unchanged
- Frontend auto-detects keyword column but doesn't require it
- ParsedStep.step_type is optional — parser is backwards-compatible

## Edge Cases
1. **Invalid keyword value:** Ignored — leaves step_type undefined → uses defaultStepType
2. **Mixed valid/invalid keywords in same file:** Valid rows get correct step_type, invalid ones get default
3. **Empty keyword cell:** Treated as unmapped for that row → default
4. **Keyword column in traditional project:** step_type set to the keyword value (harmless — traditional editor ignores step_type, Phase 4 execution ignores it too)
5. **Case-sensitivity:** "GIVEN", "given", " Given " all normalize to "given" via trim().toLowerCase()
